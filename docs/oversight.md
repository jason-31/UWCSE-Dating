# Privacy and community oversight

UWCSE.date holds personal information: who people are, what relationships they are looking for, their photos and their contact details. We don't ask users to trust the operators. Instead we commit to rules that the community can check. This document lists those rules, what they protect, what they don't, and which parts are not built yet.

**Status:** the project is in feature-first development. The rules below are binding as design constraints: new code must not make them harder to meet. Several are not implemented yet; see [TODO](#todo). Until those items are done, do not tell users that their data is protected by them.

## Goal

**No operator can access users' avatars or private contact details (WeChat, Discord) in bulk without leaving a public trace.**

This goal is deliberately narrower than "operators can see nothing". A matching service must compute matches on the server, and the operators deploy that server. So operators can always see some data, for example login emails in Cloudflare Access logs. What we can guarantee is that bulk access to the sensitive data requires a change that the community can see.

## Rules

### Code and deployment

1. **Open source.** All code that runs in production is in the public repository.
2. **CI-only deployment.** Production is deployed only by the public CI workflow, from the protected `main` branch. No person holds a Cloudflare API token that can deploy, read D1 or read R2.
3. **Configuration as code.** Environment variables, bindings, routes and Cloudflare Access settings that affect who can sign in or what code runs are declared in the repository. Changes made in the dashboard instead must appear in the published audit log (rule 9).
4. **Development mode never runs in production.** `DEV_MODE`, which lets a request choose its own identity, is honoured only for `localhost` requests, and never when Access JWT verification is configured.

### Data

5. **Personal data is encrypted at rest.** Everything that identifies or describes a person is stored sealed under keys derived from `DATA_KEY`: the whole profile (nickname, gender, program, relations, filters, notes, contacts, bio, research, the email shown on cards), sessions, ban reasons, LeetCode usernames, binding tokens and verification evidence, and uploaded avatar images. Rows are found by keyed hashes of the email or username, never by the value. What stays readable is metadata: random ids, row counts, timestamps and which random user id is on which list.
6. **Nobody holds the key.** The encryption key is a Worker secret generated by a public CI job that never prints it. Cloudflare does not let anyone read a secret back, so only the running Worker code can decrypt. Bulk decryption therefore requires deploying different code, which is visible under rules 1 and 2.
7. **The API is not a decryption oracle.**
   - Each ciphertext is bound to its owner and field, so copying it into another row makes it undecryptable.
   - Uploaded avatars are served only through short-lived signed URLs that the server issues inside cards a viewer is allowed to see. Knowing an avatar id is not enough to fetch it.
8. **No back doors in the product.**
   - There is no admin UI or endpoint that lists or shows profiles.
   - Logs never contain personal data (request bodies, contact details, profile fields).
   - Debugging uses aggregate numbers only.

### Transparency

9. **Published operator audit log.** A scheduled job publishes, without manual filtering, Cloudflare account audit events covering:
   - deployments;
   - secret and environment-variable changes;
   - API token creation and deletion;
   - Cloudflare Access configuration (identity providers, policies, service tokens);
   - routes and edge rules that can alter responses.

   A gap in the published log is itself a signal.
10. **User access logs are never published.** They contain emails, IPs and timing, which is exactly what we protect. Transparency covers what operators do, not what users do.
11. **Verifiable frontend.** The files in `public/` are served as-is, with no build step. A script in the repository compares the live files with a given commit.
12. **Privacy notice.** A user-facing notice states what is stored, who can see what, how long data is kept, and the known gaps below. Its wording must not promise more than these rules deliver.

## What the community can check

| Claim | How to check |
|---|---|
| Production runs this code | Deployment entries in the published audit log match CI runs on `main`; no other deployments appear |
| No one can read the encryption key | The key-provisioning workflow is public and never prints the key; the audit log shows no later writes to `DATA_KEY` |
| The frontend is unmodified | Run the frontend check script against the live site |
| No one can log in as other people | Session rows are sealed with `DATA_KEY`, so only the Worker can create one, and the published audit log shows no Access identity-provider, policy or service-token changes and no Google OAuth client changes |
| No standing data access | The published audit log shows when API tokens are created and deleted |

## Known gaps

These remain after every rule is implemented. The privacy notice must say so.

1. **Tampering with authorization data.** Profiles and sessions are sealed, so someone with write access to D1 can no longer edit relations, filters or visibility, or create a session: such rows simply stop opening. What remains: putting an account's random id on a list it did not join, deleting rows, and restoring an account's own older sealed profile (which would undo a change lock). The unchanged code would then show cards through the normal API, but only those that account's own sealed relations and filters allow. Mitigations to consider:
   - a per-viewer daily cap on decrypted cards;
   - publishing aggregate view counts.
2. **Timing correlation.** Access login logs (email, time) can be matched against row timestamps in D1 to link an email to a profile. Mitigation: store fewer timestamps and coarser ones.
3. **Data-plane reads may be invisible.** Reading D1 or R2 with an existing token may not appear in Cloudflare's audit log. This must be verified. Encryption (rules 5–7) means such reads yield only ciphertext, keyed hashes and metadata (known gap 2).
4. **Login emails are not secret from operators.** They appear in Access logs. Emails are also always shown on cards to other members.
5. **Cloudflare itself** (its staff and legal requests) is outside this model.
6. **Key loss is permanent.** If `DATA_KEY` is deleted or overwritten, every account, profile, session and avatar becomes unreadable and everyone must register again. This is the price of nobody holding the key.

### Abuse, capacity and launch readiness (security and performance review, 2026-11-01)

Done in the review: sign-in starts without touching D1 (signed state cookie); request bodies are size-capped; LeetCode verification claims its attempt slot atomically; per-user LeetCode queries, the session sweep and avatar pruning are indexed; static assets send nosniff, frame-ancestors, Referrer-Policy and HSTS headers.

Done afterwards:
- Per-user and per-IP rate limits (Workers Rate Limiting bindings, `src/platform/rate-limit.js`).
- Member lists and profiles are read through versioned in-memory caches (`src/platform/cache.js`): a list view reads a handful of rows instead of every listed profile, and the home page returns 24 people per relation with "Show more". Measured at 1,000 listed users: /api/people 6,003 → 5 rows, a member page 3,999 → 2-3 rows; a write costs one reload (about 1,000-2,000 rows) on the next view.
- Deleting an account records a keyed hash of the email until its change locks would have expired, and registration with that email is refused until then (`src/platform/deletions.js`).
- The profile form and About page say that two-way filters reveal which genders a person accepts.
- Avatar uploads: at most 5 attempts per email in any rolling 30 days, failed ones included (choosing an avatar is not limited or locked). Attempts are counted atomically in `avatar_upload_attempts`, keyed by a keyed hash of the email, so deleting an upload or the account does not restore them. This replaces the earlier 20-per-hour limit, which never triggered.
- Free-text profile fields are measured by weight (`public/text-weight.js`, shared by the form and the server): letters and digits count 1, Chinese and other full-width characters count 2. Limits doubled to 240 (research), 600 (bio) and 400 (relation notes), so Chinese limits are unchanged and English ones are no longer about three times shorter.
- Daily clean-up (Cron Trigger, `scheduled` in `src/index.js`, `src/platform/retention.js` and each module's `dataLifecycle.prune`): expired sessions, deletion tombstones and upload attempts; uploads no profile uses after one day; expired LeetCode binding tokens, binding locks of closed periods, and verification attempts after 7 days; closed lists (`ci_lists`, `lc_memberships`) and their cache version rows, at 08:17 UTC, soon after the Los Angeles midnight that closes them. History (check-ins, completions, badges, periods) is kept.
- Banned users sign in to a session that can only sign out and delete their data, and signed-in users who never registered can delete their uploads (`DELETE /api/account` without a profile; a button on the registration page).
- When D1's free daily row limits are used up, the API answers 503 `daily_capacity` with the time it comes back, and the front end shows the same message for Cloudflare's own 429 when the Workers request quota is used up.
- LeetCode verification can be paused with `verification.paused` in `src/challenges.config.js`: no request reaches LeetCode, and lists and history keep working.
- Hostnames: the Worker is served only at its custom domain; `workers_dev` and `preview_urls` are off (wrangler.jsonc), so no second hostname bypasses zone rules or runs preview versions against production data.

Deployment steps for these are in [deploy.md](deploy.md).
